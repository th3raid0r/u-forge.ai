# v0.1.1 Audit Remediation

## Status

Audit complete on 2026-08-11. Remediation has not started.

This plan records the findings from a repository-wide Fossil MCP `scan_all`,
targeted Fossil dead-code, clone, scaffolding, call-graph, data-flow, trace, and
blast-radius follow-ups, and independent source review by three parallel audit
tracks. Source code and tests remain authoritative where Fossil's Rust graph
disagrees with direct call sites.

No implementation is authorized by this document alone. Each work item should
land as a narrow change that preserves the contracts in `.rules`, the relevant
`.rulesdir/` guidance, and `ARCHITECTURE.md` after correcting the documented
contradictions identified below.

## Required execution order

The remediation should proceed in this order:

1. Correct active guidance that could cause destructive storage behavior.
2. Fix schema cache correctness and add immediate post-registration tests.
3. Align schema ingestion, validation, editor diagnostics, and agent edge
   behavior with the authoritative-schema contract.
4. Perform low-risk mechanical module extractions before deeper state or
   behavior refactors.
5. Consolidate repeated storage and model-selection mechanics.
6. Remove workspace-dead or cancellation-unsafe APIs only after the stated
   compatibility checks.

Do not combine the schema correctness fixes with the large GPUI or agent module
moves. The correctness changes need independently reviewable regression tests.

## 1. Correct destructive node-upsert guidance

### Confirmed issue

The implementation in `crates/u-forge-core/src/graph/nodes.rs:42-60`
correctly uses SQLite `INSERT ... ON CONFLICT(id) DO UPDATE`. Its source comment
explains that `INSERT OR REPLACE` performs a delete followed by an insert and
would fire `ON DELETE CASCADE`, deleting the node's edges and chunks.

Two active guidance files prescribe the opposite behavior:

- `ARCHITECTURE.md:117-123` says `INSERT OR REPLACE` on nodes is safe;
- `.rulesdir/rust-patterns.mdc:109-116` repeats that instruction.

Because agents must read these files before changing Rust storage, this is a
high-risk instruction bug even though the current implementation is correct.

### Remediation

- Update both guidance files to require `ON CONFLICT(id) DO UPDATE` for nodes.
- Explain that UUID foreign keys do not make `REPLACE` safe: SQLite's delete
  semantics still activate cascades.
- Keep the existing distinct rule for chunk upserts, where preserving implicit
  `rowid` is additionally required by FTS5 and sqlite-vec.

### Verification

- Retain or add a regression proving a node update preserves all existing
  edges and chunks.
- Run `make fmt-check`, `make check`, `make clippy`, and `make test`.

## 2. Fix schema registration cache invalidation

### Confirmed issue

`SchemaManager::save_schema` persists the definition and updates
`schema_cache` at `crates/u-forge-core/src/schema/manager.rs:69-76`.

Both runtime registration methods then remove the cache entry that was just
written:

- `register_object_type`, lines 234-246;
- `register_edge_type`, lines 251-263.

Strict synchronous mutation validation intentionally accepts writes when the
cache is empty for schema-less headless/bootstrap compatibility
(`manager.rs:314-322` and `:349-359`). When the registered schema is the only
loaded schema, registration therefore creates a window in which:

- immediate graph mutations can enter the schema-less compatibility branch;
- `is_valid_object_type` and `is_valid_edge_type` report false;
- synchronous editor and agent lookups cannot see the newly registered type;
- strict behavior resumes only after another `load_schema` call.

The existing registration test reloads the schema before asserting behavior,
which masks the defect.

### Remediation

- Prefer deleting both post-save invalidations because `save_schema` already
  establishes the new authoritative cache state.
- If registration logic is expected to grow, introduce one private
  load-mutate-save helper. It must publish the final cache entry exactly once.
- Keep `save_schema` synchronous as required by `.rulesdir/schema-system.mdc`.
- Preserve the schema-less compatibility path only for a graph with no loaded
  authoritative schema.

### Required tests

- Register an object type and immediately observe it through
  `is_valid_object_type` without calling `load_schema` again.
- Immediately add a conforming instance.
- Immediately reject an unknown object type, undeclared property, and missing
  required property.
- Register an edge type and immediately observe it through
  `is_valid_edge_type`.
- Immediately accept a valid endpoint pair and reject an unknown edge type and
  invalid source/target pair.
- Exercise registration when other schemas are already cached so precedence
  remains deterministic.

## 3. Unify schema parsing, normalization, and validation

### 3.1 File-contract drift

`.rulesdir/schema-system.mdc:37-62` advertises these property kinds:

- `string`, `text`, `number`, `boolean`;
- `array`, `object`, `reference`, and `enum`.

It also advertises length, numeric range, regex, and allowed-value validation.
The example places `allowed_values` beneath a `validation` object.

`crates/u-forge-core/src/schema/ingestion.rs:174-253` currently:

- recognizes only string, number, boolean, and limited arrays;
- silently maps every unknown kind to `PropertyType::String`;
- silently maps unknown array element kinds to string;
- recognizes a top-level `enum` array, not the documented nested
  `validation.allowed_values` form;
- imports only enum membership and requiredness;
- does not import length, range, or regex constraints;
- cannot construct the documented nested object or reference types.

The shipped Sine Nomine schemas mostly avoid the unsupported constructs, but a
custom schema following the documented contract can be weakened silently. That
violates the fail-closed expectations of an authoritative schema boundary.

### Remediation

- Define one explicit external schema grammar and make the documentation and
  parser agree.
- Implement recursive conversion for every accepted `PropertyType`, including
  array elements and nested object properties.
- Parse every accepted `ValidationRule` field from its documented location.
- Reject unknown property kinds, malformed item schemas, and unsupported
  validation keys with file/property context. Do not default them to string.
- Decide whether top-level `enum` remains supported as a compatibility form;
  if retained, normalize both forms through one parser and document precedence.

### 3.2 Duplicate validation engines

`SchemaManager` currently contains two partially overlapping engines:

- strict recursive property validation and general rules at
  `manager.rs:483-662`;
- shallow coercion and structured issue reporting at `manager.rs:677-783`.

They repeat type compatibility decisions but differ materially:

- strict validation checks nested arrays/objects and length/range/regex/
  allowed-value rules;
- coercing validation handles numeric and boolean string coercion and enum
  membership, but does not apply general validation rules or recursively
  validate nested values;
- editor and agent preflight use the shallow path, while final graph mutation
  uses the strict path.

This can let preflight report success before persistence rejects the same
record with a less useful error.

### Remediation

- Introduce one pure validation/normalization engine that returns a normalized
  value plus structured issues.
- Keep cache/schema lookup outside that engine.
- Let callers select policy for permitted coercions and unknown-field severity;
  do not fork type or rule evaluation again.
- Preserve these current semantics unless deliberately changed with tests:
  - `name` is a top-level metadata field, not a properties-map requirement;
  - absent and null required properties fail;
  - numeric strings may coerce to finite JSON numbers;
  - `true`, `false`, `yes`, `no`, `1`, and `0` retain their documented boolean
    coercions;
  - strict graph mutation rejects undeclared properties;
  - the empty-cache schema-less mode remains isolated to its compatibility
    boundary.

### 3.3 Editor persistence diagnostics

`crates/u-forge/src/node_editor/mod.rs:516-549` logs preflight issues, but after
calling `add_object` or `update_object` it handles only `persist_result.is_ok()`.
An error leaves the tab dirty and unsaved without surfacing the failure to the
user.

Remediation must make persistence errors explicit in the editor result returned
to `AppView`, preserve the dirty tab, and present a stable user-visible
diagnostic. Do not turn schema rejection into a generic success count of zero.

### Required validation matrix

Add table-driven tests covering:

- every `PropertyType`;
- nested arrays and objects;
- references and enums;
- min/max length and numeric value;
- regex and allowed values;
- missing and null required fields;
- unknown fields and unknown type declarations;
- successful and failed primitive coercions;
- malformed external schema definitions;
- multiple simultaneous issues with deterministic ordering;
- UI and agent preflight producing actionable diagnostics before persistence;
- strict graph mutation remaining the final authoritative guard.

## 4. Correct the agent edge contract

### Confirmed issue

`UpsertEdgeArgs.edge_type` is described as a "Freeform relationship label" at
`crates/u-forge-agent/src/lib.rs:821-830`. The tool calls
`KnowledgeGraph::connect_objects_weighted_str` at lines 949-951. That facade
always reaches strict cached-schema validation at
`crates/u-forge-core/src/lib.rs:326-352` and
`schema/manager.rs:349-389`.

`EdgeType` is open-ended as its Rust/string representation; edge mutations are
not free-form relative to loaded authoritative schemas. The current wording
encourages predictable failed tool calls and consumes agent budget.

There is adjacent stale API text:

- `SchemaDefinition::prompt_summary` at
  `crates/u-forge-core/src/schema/definition.rs:49-55` says edge types are
  intentionally omitted because they are freeform;
- the actual bounded agent summary correctly includes edge records and endpoint
  constraints at `crates/u-forge-agent/src/budget.rs:175-207`;
- `KnowledgeGraph::schema_prompt_summary_all` is a legacy unbounded wrapper and
  has no first-party consumer.

### Remediation

- Change tool argument and description text to require an edge type from the
  active schema and a permitted endpoint pair.
- Add an edge-name preflight that returns sorted valid choices before invoking
  the facade. Keep facade validation authoritative to avoid time-of-check/time-
  of-use assumptions.
- Ensure the bounded schema prompt continues to include complete edge records.
- Delete or deprecate the legacy unbounded summary methods after checking for
  external API commitments. If retained, correct their edge semantics and make
  them difficult to use accidentally in model requests.

### Required tests

- Unknown edge type reports valid schema choices.
- Known edge type with an invalid source or target reports the endpoint rule.
- Valid edge mutation succeeds and re-embeds both endpoints.
- A self-edge embeds the endpoint only once.
- Cancellation before persistence still prevents the graph write.

## 6. Separate chat execution from rendering and persistence

### Evidence

`crates/u-forge/src/chat_panel.rs` is 2,703 lines. Its state at lines 76-168

- incremental message entities and pending assistant presentation;

### Remediation

- Extract an internal chat-run state/event reducer for:
  - ensuring or consuming the pending assistant row;
  - applying agent events;
  - applying direct-stream tokens;
  - tool-call/result transitions;
  - one terminal success/error/cancellation transition.

  behavior is covered. Do not introduce per-message subscriptions or new entity

### Verification

## 7. Modularize `u-forge-agent` and centralize its tool catalog

### Evidence

`crates/u-forge-agent/src/lib.rs` is 1,945 lines and contains:

- history and validation APIs at lines 39-171;
- result formatting and three search tools at lines 173-633;
- node and edge mutation tools at lines 634-1004;

- actual Rig registration at lines 1319-1347.

Descriptions and parameter schemas are built by constructing the same tools

### Remediation

  - `tools/search.rs`;
  - `tools/mutation.rs`;
  - `tools/validation.rs`;
  - `agent.rs`;

- Add a parity test proving the catalog, validator, budgeted definitions, and
  registered tool set expose the same names.
- Keep heterogeneous Rig tool construction explicit where the type system makes
  a generic registry obscure. The catalog should remove metadata drift, not
  erase meaningful concrete tool types.

### Secondary search-tool consolidation

The three search tools overlap semantically:

- semantic search invokes the shared hybrid pipeline with `alpha = 1.0`;
- hybrid search accepts arbitrary alpha and can express pure semantic or pure
  keyword search;
- FTS retains a separate hydration/formatting path.

First unify their internal execution and formatting while preserving all three
model-visible names. Use agent evaluations before removing a tool: fewer tool
definitions save context, but the specialized names may improve model choice.

## 8. Consolidate embedding-lane storage mechanics

### Evidence

The standard and high-quality embedding lanes repeat approximately 127

- vector upserts in `graph/fts.rs:68-108` and `:186-219`;

  controlled table name, expected dimension, fingerprint key, and diagnostic
  label.
- Route internal standard/HQ operations through shared lane-parameterized

- Chunk `rowid` remains the vector identity.
- Provider fingerprints initialize only for empty lanes.
- Populated legacy lanes without identity remain excluded until reindexed.
- Reset clears only the selected regenerable lane.

### Verification

Parameterize existing storage cases across both lanes: dimension mismatch,
missing chunk, re-upsert, ANN ordering and limits, empty index, cascade cleanup,
fingerprint mismatch, unidentified legacy vectors, reset, and stats.

## 11. Compatibility-gated deletions

Fossil treats public Rust APIs as entry points, so direct workspace search found
stronger deletion candidates than its reachability output. These deletions must
check external API expectations because the crates expose public symbols even
though the workspace has no consumers.

### 11.1 Uncancellable `GraphAgent` convenience APIs

The desktop calls only
`prompt_stream_with_profile_and_cancellation` from
`crates/u-forge/src/chat_panel.rs:902-915`.

These public methods have no first-party consumer:

- `prompt_stream`, `u-forge-agent/src/lib.rs:1355-1370`;
- `prompt_stream_with_params`, lines 1376-1398;
- `prompt_stream_with_profile`, lines 1402-1423;
- non-streaming `prompt`, lines 1683-1715.

They manufacture an inaccessible `CancellationToken`. The non-streaming method
can run mutation tools without caller-controlled cancellation, conflicting with
the repository's explicit parent-lifetime contract.

Remove them in the prerelease API or replace them with an owned operation handle
that exposes cancellation and observable termination. Audit `pub use rig` at
line 1720 at the same time; remove it unless deliberate external compatibility
requires it.

### 11.2 Unused RAG facade

`crates/u-forge-core/src/rag.rs` is a 142-line public facade that claims
`ChatPanel` consumes it. Repository search found no consumer of `RagContext`,
`format_search_context`, or `build_rag_messages` outside the module and its
re-export. Current chat paths assemble their own requests.

Delete the module and re-exports after confirming no external consumer is part
of the v0.1.1 compatibility surface.

### 11.3 TypeScript runtime skeleton

`crates/u-forge-ts-runtime/src/lib.rs` contains two comments and no public
symbols or runtime implementation. Its manifest declares `u-forge-core`, full
Tokio, serde, serde_json, and anyhow despite having no code or consumers.
Because workspace membership is `crates/*`, it participates in workspace
resolution and builds.

`.plans/feature_TS-Agent-Sandbox.md` explicitly says implementation is blocked
on a pinned `deno_core` API, threat model, resource-control proof, and v1 scope.
That design gate preserves the intended boundary better than an empty crate.

Preferred remediation:

- delete `crates/u-forge-ts-runtime`;
- update `Cargo.lock` and descriptive architecture references;
- keep the design gate and recreate the crate only after approval.

If retaining the directory is a deliberate project signal, at minimum remove
its speculative dependencies and exclude it from normal workspace targets.

### 11.4 Legacy schema prompt API

After the edge-contract work, audit removal of:

- `KnowledgeGraph::schema_prompt_summary_all`;
- `SchemaDefinition::prompt_summary`.

The workspace agent already uses `merged_schema_definition` plus bounded,
whole-record selection. Keeping an unused unbounded prompt string API creates a
future path around the agent budget ledger.

### 11.5 Serialized schema fields with no production consumer

Two low-priority candidates require persisted-schema compatibility review:

- `ValidationRule.required` is written during ingestion but production
  requiredness is enforced through `ObjectTypeSchema.required_properties`;
- `PropertySchema.default_value` and `with_default` have no production
  consumer.

Do not remove serialized fields without deciding migration and backward
compatibility for existing persisted schema JSON.

## 13. Clone findings explicitly rejected

Do not create abstractions for these groups merely to reduce Fossil counts.

### Declarative default schema builders

All 16 production schema groups at the 12-line threshold are combinatorial
pairings among default object and edge builders in
`schema/definition.rs:163-323` and `:570-641`. They are declarative domain data.
Tables or macros would obscure differences and make review harder.

If hardcoded defaults and file-based defaults are later unified, do so as a
source-of-truth product decision, not as clone-count cleanup.

### Queue typed capability APIs

The queue produced zero production clone groups at six lines. Its apparently
repetitive methods encode distinct job/result types, cancellation points,
stream ownership, and lifecycle outcomes. Do not replace them with an untyped
generic queue abstraction.

### UI component constructors

Fossil matches among `Button`, `StatusItem`, and `MenuItem` constructors are
ordinary builder symmetry. A common superclass-style abstraction would not
reduce GPUI behavior risk.

### Small provider and validation fragments

- Provider constructor overlap across reranking and transcription is normal
  trait implementation structure.
- Small name-collection and error-construction matches in `SchemaManager` do
  not justify generic helpers ahead of the unified validation engine.
- Cross-domain matches involving vendored `cosmic-text` are lexical
  coincidences.

## Fossil limitations observed

For this Rust workspace, Fossil did not reliably resolve:

- same-named inherent methods;
- method-call syntax across facade layers;
- GPUI closure and action callbacks;
- trait-provided render entry points;
- paired cfg definitions;
- implicit format-string captures;
- destructured or pattern-bound locals;
- several direct storage/facade call chains.

Examples of direct source paths that Fossil reported disconnected included
agent tool cancellation setters, embedding calls into missing-vector storage,
and hybrid search into semantic storage. Use Fossil to locate review leads and
local duplication, but require `rg`, compiler/clippy diagnostics, direct source
inspection, and tests before deletion or blast-radius decisions.

## Completion criteria

This remediation is complete only when:

- active storage guidance agrees with safe node-upsert source behavior;
- registration leaves authoritative schemas immediately visible and enforced;
- external schema files either fully implement the documented grammar or fail
  closed with actionable diagnostics;
- one validation engine governs coercion, recursive types, and validation rules;
- editor persistence failures are visible to the user;
- agent edge descriptions and preflight match strict loaded-schema behavior;
- AppView Lemonade lifecycle, chat execution, and agent tools have clear module
  boundaries without changing cancellation or GPUI invalidation semantics;
